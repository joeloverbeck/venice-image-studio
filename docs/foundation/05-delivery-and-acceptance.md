## Minimum later useful-slice acceptance

The next implementation, if selected, should deliver one complete generation-to-
library path, including failures, before expanding to editing or upscaling.
Use an owner-supplied private prompt over 1,500 characters and a suitable model;
do not publish that prompt or output as a fixture without explicit authorization.
The bounded provider experiment needs an agreed model, request count and spending
allowance. An absent numeric allowance here is not permission to invent one.

Evidence must demonstrate:

1. Documented local setup and one ordinary startup path; after setup, the owner
   can return without manually coordinating frontend/backend development servers.
2. Informed model choice, correct sizing and safe-mode display, exact submitted
   prompt, a visible real result and inspection at useful detail. Test supported
   seed controls without claiming cross-model or permanent reproducibility.
3. Original-byte download and automatic external save with matching hash/recipe;
   reopen after process restart and reuse settings without a paid call.
4. A materially different model/sizing path. Cover the >7,500 schema discrepancy
   separately before advertising verified support at that length.
5. Offline response fixtures covering string/object/plain-text/unknown errors,
   explicit refusal, partial 200, all-refused 422, non-policy 422, blur/violation
   flags, missing reasons, retry advice/suggestions and unknown refund status.
   Verify source-attributed private/anonymized/uncensored/unknown UI states.
6. Duplicate-click/reload/interrupted-request behavior, image decode/size failures,
   save failure and crash recovery, redaction and path/origin protection. No
   unintended paid retries or changes to prompts/models. Fixtures must be synthetic
   or explicitly cleared, and must not require generating erotic content.

Run focused Rust, browser and integration checks appropriate to the implemented
behavior. Compilation or a screenshot is not proof of provider behavior, local
durability or owner usability. The owner must inspect the actual launch, prompt
entry, model explanation, image viewing and return-to-library experience before
“easy to use” is accepted. Recurrent usefulness requires later ordinary return
use, not a second scripted demonstration presented as demand.
